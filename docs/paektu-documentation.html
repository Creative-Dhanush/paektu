Paektu

Security controls as code, with documentation drift detection. Your automated checks pass, your dashboard is green, and the document your auditor actually reads has been quietly wrong for nine months. This is the tool that catches that.

What it is

Paektu evaluates security and compliance controls defined as YAML, collects tamper-evident evidence, maps findings to SOC 2, ISO 27001, HIPAA, PCI DSS and GDPR clauses, and reports drift against a recorded baseline.

It does one thing no other compliance tool does: it treats the written narrative attached to each control as a control surface in its own right, with its own evidence and its own failure modes.

The name is the highest peak on the Korean peninsula — the fixed landmark you take your bearings from when everything else on the horizon has moved.

paektu check
STATUS CONTROL     SEV       MESSAGE
------------------------------------------------------------------------
PASS   SEC-004     high      logging.retention_days is 180 (minimum 90) (doc)
------------------------------------------------------------------------
21 controls   pass 21   fail 0   warn 0   error 0   skip 0
posture score 100.0%
documentation drift on 1 control(s): SEC-004
audit ready: no

Every control passes. The score is 100%. And it is not audit ready, because one narrative no longer describes the system it claims to describe. That line is the product.

Why it exists

A compliance programme has three artifacts per control, not two.

ArtifactWho consumes itAutomated today?
The control
What is required		Engineers, toolingYes
The evidence
What a machine observed		Auditors, toolingYes
The narrative
Prose explaining what it does and why it is adequate		The auditor, the regulator, the enterprise buyer, and now AI agentsNo. Nothing watches it.

Every platform on the market automates the first two. The third — the part a human being reads and forms a judgement on — is a text box somebody filled in once.

The failure, concretely

January
An engineer writes: “Audit logs are retained for 90 days in line with PCI DSS 10.5.” True at the time.

April
The platform team raises retention to 180 days. The automated check still passes — 180 exceeds the 90-day floor. Nobody edits the paragraph.

October
An auditor reads a document asserting 90 days, for a system that keeps 180. The check was green the entire time.

That is the benign direction. The dangerous one is the reverse: retention drops to 30 days, the narrative still claims 90, and the documentation is now actively misleading a regulator while the failure sits unread in a backlog.

Neither case is detected by any tool that watches only controls and evidence.

The asymmetry

Detecting narrative drift costs one CI job. Not detecting it costs a widened audit scope and possibly a finding against a control that was working correctly the whole time.

Install

Python 3.10 or newer. The only runtime dependency is PyYAML.

shell
git clone https://github.com/Creative-Dhanush/paektu
cd paektu
pip install -e ".[dev]"

paektu --version

If paektu is not on your PATH, python -m paektu is identical and is the safer form inside CI, where PATH after a pip install is not always what you expect.

Quickstart

1. Evaluate everything

paektu check
FAIL   SDLC-001    high      no CI pipeline definition found
WARN   DOC-001     high      narrative exists but has never been attested
PASS   AC-001      critical  identity.mfa_enforced is declared true
------------------------------------------------------------------------
21 controls   pass 19   fail 1   warn 1   error 0   skip 0
posture score 90.5%
audit ready: no

Failures sort to the top, because that is what you came to see.

2. Narrow the run

shell
paektu check --framework SOC2       # one framework
paektu check --min-severity high    # skip low-stakes controls
paektu check --control SEC-001      # one control
paektu check --tag observed         # only machine-verified controls

That last filter matters. Controls tagged observed are the ones a machine actually verified, as opposed to those resting on a declaration. When somebody asks what you can genuinely prove, that is the filter to reach for.

3. Record a baseline

shell
paektu check --save-evidence --label baseline

4. Watch drift get caught

Change a word inside any narrative: block — in controls/data-protection.yaml, turn SEC-004's “ninety day floor” into “thirty day floor” — then re-run. The fastest route is the shipped demo, which does this and restores the file on exit:

bash examples/demo.sh
PASS   SEC-004   high   logging.retention_days is 180 (minimum 90) (doc)

baseline 2026-08-19T09:14:02Z  ->  current 2026-08-19T11:40:55Z
score 100.0% -> 100.0% (+0.0)

DOCUMENTATION DRIFT (1)
  SEC-004 narrative changed since attestation

blocking: yes

The score did not move. A documentation regression is invisible to a posture score, which is exactly why it needs its own category and its own blocking behaviour.

Narrative fingerprints

Each control carries a narrative_hash: a fingerprint of the prose a person last reviewed. On every run the narrative is re-hashed and compared.

Whitespace does not count

Fingerprints are computed over whitespace-normalised text. Reflowing a paragraph is not drift; changing a word is. A detector that fires when someone rewraps a line gets muted within a week, and a muted detector is worse than none.

Three outcomes, kept separate

StateStatusMeaning
No narrative at allFAILNever written
Narrative, no fingerprintWARNWritten, never reviewed
Fingerprint mismatchFAILReviewed, then changed

The middle case warns rather than fails because a narrative awaiting first review is a normal state during authoring. The third fails because prose that drifted after sign-off is a defect, and it is the one an auditor will find. Collapsing them would hide the difference between work never started and work that has silently rotted.

Evidence typing

The second load-bearing idea: not all evidence is equal, and the tool refuses to pretend otherwise. Every result records how the fact was established.

TypeMeaningStrengthExample
observedA machine read your repositoryStrongestNo AWS keys in tracked files
attestedA named person confirmed it on a recorded dateMiddleAccess review performed
declaredSomebody typed true in a config fileWeakestMFA is enforced

The type is preserved through checks, reports and stored artifacts, so a reader can tell which findings rest on a machine and which rest on somebody's word.

Attestation rejects a tickbox

Higher-risk controls use the posture.attested check, which refuses a bare true and demands a name and a date. 

# fails: a tickbox is not an attestation
access_review: true

# passes
access_review:
  confirmed: true
  attested_by: security-lead
  attested_on: 2026-08-15

An access review with nobody's name against it is not a review.

Attestation

Resolving drift is one command, and it is deliberately a human act.

paektu attest SEC-004
attested SEC-004: b716408a8fb5eaf5 -> eb3deb21654b61fc

The tool will never attest on its own. Not as a safety limitation — because the fingerprint's entire meaning is “a person read these words and stands behind them.” A tool that could sign that for you would be recording a fact about itself, and the mechanism would be theatre.

For the same reason attest writes a targeted line edit into the YAML rather than re-serialising the file. Round-tripping through a YAML dumper would reflow comments and reorder keys, producing a diff nobody can review — and an unreviewable diff in the middle of an attestation workflow defeats the purpose.

paektu attest all covers every narrative currently stale or never attested. Use it sparingly: attesting twenty narratives in one command is a fair signal that nobody read them.

Shared filters

Accepted by check, report and drift, and they combine with AND: --path, --controls, --framework, --control, --tag, --min-severity.

If nothing matches, the command exits 2 rather than reporting a vacuous pass. An empty run that looks like success is worse than an error.

Reading the summary

Posture score is the share of evaluated controls that passed. Skipped controls are excluded rather than counted as failures, because a control that does not apply should not drag the number down.

Audit ready is stricter: it requires no failures and no narrative drift. A run can score 100% and still not be audit ready, which is the entire point of tracking prose separately.

Exit codes

Part of the contract, because the main consumer is a pipeline rather than a person.

CodeMeaning
0Everything the command asked about is satisfied
1A control failed, or drift was detected
2The tool could not run: bad config, missing controls, unreadable YAML
Why 1 and 2 are separate

A pipeline must distinguish “your compliance posture regressed” from “the compliance tool is broken.” Collapse them and a typo in a control file looks like a real finding — which is how teams learn to ignore the signal entirely.

Checks

Fourteen checks in three families. The does not prove column matters most: a check's limits determine how much weight a pass deserves, and a narrative that repeats those limits is what makes a report trustworthy.

repo.* — observed

These read files on disk. They verify what is committed, not what a hosting provider's dashboard claims. A branch protection rule configured in a web UI and never captured in the repo leaves no evidence trail.

CheckParamsProvesDoes not prove
repo.file_presentany_ofA file with that name existsThat its contents are correct, current or non-empty
repo.no_hardcoded_secretsallow_pathsNo string matching a known credential shape is in the working treeThat the repo is clean. Misses git history and high-entropy strings matching no known shape
repo.dependencies_pinnedmanifestsDeclared dependencies carry version operatorsThat constraints are tight, or that transitive deps are pinned
repo.ci_configured—A pipeline definition existsThat it passes, runs on the right branches, or does anything at all
repo.tests_presentpaths, min_filesTest files existCoverage, that tests pass, or that they assert anything meaningful
repo.gitignore_excludespatternsThe patterns are listedThat nothing matching them was already committed

repo.tests_present returns WARN below min_files rather than FAIL, on the reasoning that a token single test file is worse than none because it creates a false impression of coverage.

posture.* — declared or attested

These read paektu.yaml for facts a repository cannot establish. A missing key is always FAIL, never SKIP — silence is not a control.

CheckParamsAsks
posture.is_truekeyIs this explicitly true?
posture.at_leastkey, minimumDoes it meet a numeric floor?
posture.at_mostkey, maximumDoes it stay under a ceiling?
posture.one_ofkey, allowedIs it in an approved set?
posture.attestedkeyNamed signer and date recorded?

A non-numeric value where a number is expected returns ERROR rather than FAIL, because that is a defect in the posture file rather than a finding about the system.

docs.* — observed

CheckParamsAsks
docs.narrative_current—Does the prose match its attestation?
docs.pages_presentpages, min_charsDo the docs cover a minimum surface, without stubs?
docs.evidence_explainedmarkersDoes the narrative state its provenance?

The min_chars floor exists because an empty quickstart.md satisfies a naive existence check while helping nobody — and a stub is arguably worse than an absence, since it stops anyone noticing the gap.

Anatomy of a control

- id: SEC-004
  title: Audit logs are retained long enough to investigate an incident
  description: >
    Security-relevant logs are kept for at least ninety days so that an
    incident discovered late can still be reconstructed.
  check: posture.at_least
  severity: high
  owner: platform-team
  tags: [logging, data]
  params:
    key: logging.retention_days
    minimum: 90
  frameworks:
    - framework: PCIDSS
      clause: "10.5"
      title: Audit log retention
  narrative: >
    Retention is declared in paektu.yaml and compared against a ninety day
    floor, chosen because PCI DSS requires three months of immediately
    available logs. This control checks the declared figure and cannot
    confirm logs are actually present for that whole window.
  narrative_hash: eb3deb21654b61fc
FieldRequiredPurpose
idYesStable identifier, unique across every file
titleYesOne line, readable by a non-engineer
descriptionYesWhat the control requires
checkYesName of a registered check
severityNolow / medium / high / critical. Default medium
ownerNoWho answers for it. Appears in reports
tagsNoFree-form. Filter with --tag
paramsNoPassed to the check; shape depends on the check
frameworksNoClause citations. Drives coverage reporting
narrativeNoProse for the auditor. Fingerprinted
narrative_hashNoWritten by paektu attest, never by hand

Duplicate ids are a fatal error rather than a warning. Two controls answering to one name means a report can cite a passing result while a failing one exists.

Writing a narrative that earns its place

Three things make one useful:

  • Say whether the fact was observed or declared. The single most valuable sentence available. It tells a reader exactly how much weight to give the pass.
  • State the limits. A narrative admitting that a regex scanner misses git history is more trustworthy than one implying comprehensive coverage — and a reader who finds an unstated limit themselves stops believing the rest of the document.
  • Explain the numbers. Ninety days and twelve hours are policy choices, not natural constants. Say where they came from, and say when no framework prescribes them.

The posture file

paektu.yaml holds the facts that cannot be established by reading a repository: what the identity provider enforces, how long logs are kept, when somebody last restored a backup. 

posture:
  identity:
    mfa_enforced: true
    least_privilege: true
    privileged_session_hours: 8

    access_review:
      confirmed: true
      attested_by: security-lead
      attested_on: 2026-08-15

  data:
    encryption_at_rest: true
    min_tls_version: "1.2"

  logging:
    retention_days: 180
The trust model, stated plainly

Editing this file to make a check pass, without changing the underlying system, is compliance theatre. The tool cannot stop you. It can only make sure the resulting report says declared rather than verified, so a reader knows exactly how much weight the claim carries.

Quote version strings. min_tls_version: 1.2 parses as the float 1.2 and will not match the string "1.2" — a recurring source of confusing failures.

Drift detection

Compliance rots quietly. A control that passed in March and fails in August is the interesting event, and it is invisible if you only ever look at the current run in isolation.

CategoryBlocks?MeaningWhat to do
RegressionyesPassed before, fails nowFix the system
Narrative driftyesProse moved away from its attestationRe-review the words
ImprovementnoFailed before, passes nowUpdate the narrative to match
StructuralnoControls added or removedReview the scope change

Improvements deserve a note. When a control starts passing, its narrative is usually now wrong in the other direction — it describes a gap that no longer exists. That is why improvements are surfaced rather than silently celebrated.

Regressions are ordered worst-first by severity, so a truncated console view still shows what matters.

Evidence store

An auditor does not want a dashboard; they want artifacts with dates on them. Each run is written to a timestamped JSON file under .paektu/evidence/, with a manifest so the history is walkable without a database.

Runs are append-only by design. Nothing mutates or deletes a previous run, because a compliance tool that can quietly rewrite its own history is worth very little as a source of truth.

paektu verify
verified 3 stored run(s)
all evidence artifacts match their recorded hashes
Reported problemMeaning
manifest hash disagrees with fileThe manifest entry was altered
contents changed after recordingThe artifact was edited
missing or unreadableThe file is gone

The store is gitignored, because it is generated output. That has one consequence worth knowing: CI has no baseline for drift unless you commit one deliberately or cache the directory between runs.

Framework crosswalk

One control usually satisfies clauses in several frameworks at once: requiring MFA helps with SOC 2 CC6.1, ISO 27001 A.5.17 and PCI DSS 8.4 simultaneously. Doing that mapping by hand in a spreadsheet is how organisations end up answering the same question four times with three different answers.

paektu frameworks SOC2
SOC2: 11/12 catalogued clauses addressed (91.7%)

  CC6.1            Logical access security software and infrastructure
                   controls: AC-001, AC-004, SEC-001, SEC-005
  CC6.2            Registration and authorisation of new users
                   controls: AC-003

  gaps (1): CC6.8

Output separates three things:

  • mapped — catalogued clauses your controls cite
  • gaps — catalogued clauses nothing cites
  • uncatalogued clauses cited — clauses your controls reference that the catalogue does not know, which usually means a typo

That last category exists so a mapping error cannot masquerade as coverage. Coverage counts clauses addressed, not clauses passed. It is a map of what the control set talks about, and it is not a compliance claim.

Framework names are fuzzy: soc2, SOC 2 and soc-2 all resolve.

CI integration

name: compliance

on: [push, pull_request]

jobs:
  posture:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -e .

      - name: Verify evidence integrity
        run: paektu verify

      - name: Check posture
        run: paektu check --strict

      - name: Publish report
        if: always()
        run: paektu report --out posture.md

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: posture-report
          path: posture.md

if: always() on the report step matters. The run you most want a report from is the one that just failed.

Use --strict on your default branch. Without it a documentation regression merges silently, which is the exact failure this tool exists to prevent.

Architecture

paektu/
├── models.py       Control, Evidence, CheckResult, RunSummary, fingerprinting
├── registry.py     YAML loading, strict validation, attestation writing
├── engine.py       Evaluation. A raising check becomes ERROR, never aborts the run
├── checks/
│   ├── repo.py     observed  — reads your repository
│   ├── posture.py  declared  — reads paektu.yaml
│   └── docs.py     observed  — narrative currency, doc surface
├── evidence.py     Append-only store, content hashes, tamper detection
├── drift.py        Four-category comparison against a baseline
├── frameworks.py   Clause catalogue and crosswalk
├── report.py       Console tables and audit Markdown
└── cli.py          Seven subcommands, three exit codes

One runtime dependency: PyYAML. No network calls, no cloud SDKs, no credentials. That constraint is why runs are reproducible and why the tool can be pointed at any checkout — and it is the honest reason declared controls exist at all.

Reports are Markdown rather than PDF because Markdown diffs. Seeing what changed between last quarter's report and this one is worth more than typographic polish.

Writing a check

A check is one decorated function. Nothing else in the codebase needs to change.

from ..models import Evidence, Status
from . import Target, register, result


@register("repo.readme_mentions_security")
def readme_mentions_security(control, target: Target):
    """One-line summary. Shown by `paektu checks`."""
    body = target.read("README.md")
    if not body:
        return result(control, Status.SKIP, "no README.md to inspect")

    needle = control.params.get("phrase", "security")
    if needle.lower() in body.lower():
        return result(
            control, Status.PASS, f"README mentions {needle!r}",
            evidence=[Evidence(
                control_id=control.id,
                collector="repo.readme_mentions_security",
                summary=f"found {needle!r}",
                detail={"phrase": needle, "chars": len(body)},
            )],
        )

    return result(
        control, Status.FAIL, f"README never mentions {needle!r}",
        remediation="add a security section pointing at SECURITY.md",
    )

The Target API

target.root                              # Path to the repository root
target.path("docs", "index.md")          # build a path beneath root
target.exists("LICENSE", "LICENSE.md")    # first candidate, or None
target.read("README.md")                 # text, or "" if unreadable
target.posture_get("a.b.c", default=None)  # nested posture lookup

Rules worth following

RuleWhy
Return, do not raiseThe engine catches exceptions and converts them to ERROR so one broken check cannot cost the whole run — but a returned status carries a better message than a caught traceback
SKIP means “not applicable”A missing manifest is a skip; a manifest full of unpinned packages is a failure. Conflating them makes the score meaningless
WARN means “present but inadequate”One test file is a warning, not a pass and not a failure. Warnings do not block unless --strict
Attach evidence with a detail payloadIt gets hashed and the hash lands in the audit report. Evidence a reviewer cannot reproduce is decoration
Populate remediation on every failureA finding with no next action becomes a permanent backlog item
Serialise with default=strYAML turns attested_on: 2026-08-15 into a date. A json.dumps without a fallback encoder crashes on the first attested control — there is a regression test for this because it already happened once

Troubleshooting

SymptomCause and fix
paektu: command not foundNot on PATH. Use python -m paektu, which is equivalent and safer in CI
error: no controls foundWrong directory, or --controls points somewhere empty. Exits 2, because a run with nothing to check is a broken invocation, not a clean bill of health
error: no controls matchedFilters combine with AND and eliminated everything. Check paektu frameworks --list
invalid YAMLUsually an unquoted clause. clause: 10.5 parses as a float; write clause: "10.5"
duplicate control idTwo controls share an id, usually after copying a block. Fatal by design
unknown check 'posture.is_ture'Typo, or a check that is never imported. Run paektu checks. New checks must live in repo.py, posture.py or docs.py
not declared in paektu.yamlMissing posture key. Mind the nesting: identity.mfa_enforced is two levels deep
attested fails though the value is trueWorking as intended. That check wants confirmed, attested_by and attested_on
one_of fails on a correct-looking valueYAML type coercion. Run --format json and read detail.value to see what arrived
A narrative keeps failing after you fixed the textFixing the words is not attesting them. Run paektu attest ID
Score is high but audit ready is noWorking as intended. The score counts passes; readiness also requires no narrative drift
Passes locally, fails in CIEither CI uses --strict and you did not, or you have untracked files. Observed checks read the working tree, so an uncommitted LICENSE passes locally and fails in CI
drift says there are no stored runsRecord a baseline: paektu check --save-evidence. The store is gitignored, so CI needs one committed or cached

Limitations

Stated plainly, because compliance tooling has a reputation for implying more than it delivers. Every one of these also appears in the relevant control's own narrative.

LimitationDetail
It does not make you compliantIt checks what it says it checks. A green run is not an audit opinion
It cannot verify a declarationWrite mfa_enforced: true without enforcing MFA and it reports a pass. It labels that pass declared — the point of the labelling — but it cannot go and look
The secret scanner is a coarse netRegex over the working tree. Misses credentials removed from the tree but still in git history, and high-entropy strings matching no known shape
It cannot tell if a narrative is accurateOnly whether a person confirmed it since it last changed. A confidently wrong narrative, attested, passes cleanly
Attestation is only as good as the reviewattest all after skimming is indistinguishable, to the tool, from a careful reading
Drift is only tracked in prose it holdsIf your real documentation lives in a wiki and the narrative is a summary, the fingerprint tracks the summary. The wiki can rot untouched
docs.evidence_explained is a keyword searchEasy to satisfy without meaning it. Value is as a review prompt, not an assurance
Framework coverage is partialCounts clauses addressed, not clauses passed, and lists gaps rather than hiding them
No live cloud scanningBy design. That is what the posture file and the declared label exist to be honest about
What it does buy you

The failure mode changes shape. Instead of prose rotting invisibly for nine months, a diff to a narrative surfaces in the next CI run and lands in front of whoever owns the control.
